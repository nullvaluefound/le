# Distribution operations

## Assessment and implementation plan

The starting application was a single Python script with Colorama 0.4.6,
a Windows PyInstaller specification, existing PE binaries, `--help`, and
`--version` reporting `Directory Tree Printer 1.0`. The application folder had
no Git metadata, workflows, packaging system, or existing release process.
Its `test/` folder contained example directory data rather than automated tests.

The implementation preserves `main.py`: add native installers and release
helpers; verify platform/architecture/version/hash; package Debian artifacts;
generate native portable WinGet manifests; sign and validate APT metadata;
then automate tested builds and protected publication.

Release `v1.0.0` is public. The production APT repository is deployed and

including HTTPS signature verification, package installation, CLI/JSON output,
purge, and separate repository removal. A second publication verified restoring

and weekly expiry refresh are enabled with `LE_APT_ENABLED=true`.
WinGet manifests are validated and submitted in [PR #474502](https://github.com/microsoft/winget-pkgs/pull/474502). Microsoft validation, review and catalog publication remain pending.

The production secrets are restricted to the `apt-release` environment on
`main`. Pages deployment is also restricted to `main`; release publication uses
version tags. Main rejects force pushes and deletion, and version tags reject
rewriting and deletion. These rules do not require a pull-request review for
ordinary owner-authorized changes.

`packaging/distribution.json` is the configuration authority. A missing signing
fingerprint or protected signing secret deliberately blocks APT publication.
Native GitHub Releases and WinGet staging can proceed independently.
Synthetic `LicenseRef-Packaging-Test-Only` metadata and ephemeral keys are used
only for tests and are explicitly rejected by production publication validation.

Local tests prove manual install/uninstall behavior and repository signatures.
The checked-in CI workflow runs native builds and disposable Linux container
tests; a green CI run is the evidence for that commit, not this document alone.
ARM64 is configured but disabled until explicitly enabled and tested. Neither
the existence of manifests nor a successful build means community WinGet
approval, GitHub Release publication, or APT Pages deployment has occurred.

## Native release artifacts

| Artifact | Native runner |
|---|---|
| `le-windows-amd64.exe` | Windows AMD64 |
| `le-windows-arm64.exe` | Windows ARM64, opt-in |
| `le-linux-amd64` | Linux AMD64 |
| `le-linux-arm64` | Linux ARM64, opt-in |

The source version remains the application's existing CLI version. The build
accepts `1.0` as equivalent to release `1.0.0`, but rejects a new tag that does
not match `--version`. Change the application version deliberately before a
future release; packaging does not rewrite it or inject a hidden CLI override.

PyInstaller, hooks, and build dependencies are pinned in
`packaging/requirements-build.txt`. `SOURCE_DATE_EPOCH` comes from the tag
commit in release automation. Artifacts are verified by PE/ELF headers, native
execution, CLI help/version smoke tests, and SHA-256. Build environments can
still affect byte-for-byte output; hashes describe the actual produced files.

Executables bundle Python and Colorama, but are dynamically linked to the OS
C runtime. Linux `.build.json` records a conservative minimum glibc equal to
the build baseline, and Debian Depends enforces it. Local Ubuntu 24.04 artifacts
use glibc 2.39. AMD64 CI uses Ubuntu 22.04/glibc 2.35 and tests Ubuntu 22.04 and
Debian 12. Optional ARM64 builds use newer runners and are not advertised for
older distributions without matching validation. No static-linking claim is made.

## Manual installers and ownership

The root `install.ps1`, `uninstall.ps1`, `.bat` wrappers, `install.sh`, and
`uninstall.sh` are generated by `python packaging/generate_manual.py` from
shared templates under `packaging/windows/` and `packaging/linux/`.
CI refuses generated-file drift. The delivered scripts are self-contained;
they do not require Python, pip, jq, or a separately downloaded helper.

Windows needs PowerShell 5.1+ and the OS .NET runtime. Bash installers use
Bash, GNU coreutils, `awk`, `grep`, and `curl` for online downloads. Local
installation needs no network. Both require a trusted SHA-256 or SHA256SUMS
entry for local binaries, verify architecture, run the candidate, and smoke-test
the installed command. Downloaded files come from version-specific or latest
GitHub Release HTTPS URLs with their matching checksum file.

Windows installs into `%LOCALAPPDATA%\Microsoft\WindowsApps\le.exe`, honoring
the selected project location rather than creating another PATH directory.
The ownership record is `%LOCALAPPDATA%\le-manual\ownership.json`. The script
uses .NET user-environment APIs, never `setx`, and removes only the PATH entry
it originally added. WindowsApps is shared and is never recursively removed.
Existing WinGet links or unowned files are refused. WinGet installations must
be upgraded or removed through WinGet.

Linux defaults to `~/.local/bin/le`, with state at
`${XDG_STATE_HOME:-$HOME/.local/state}/le`. It adds exact marked blocks to
`.profile`, `.bashrc`, and `.zshrc` only if necessary.
For Bash login shells it also updates the existing `.bash_profile` or
`.bash_login` selected by Bash's precedence, without creating either file.
Existing bytes and later user edits outside the block are preserved on removal. Changed installer-owned
blocks are preserved with an actionable error. Symlinked profiles are not edited.
An optional `--system` mode targets `/usr/bin/le` and `/var/lib/le-manual`; it
requires an explicitly elevated shell and never invokes sudo itself.

Repeated installation is an upgrade; repeated removal is safe. Modified owned
executables are preserved rather than silently overwritten. Unrelated files
in an installation directory remain. An unrelated discoverable `le` command
requires explicit `--allow-shadow` for a separate per-user Linux installation.

Examples from a checked-out source tree after building:

```powershell
.\install.ps1 -LocalBinary .\release\le-windows-amd64.exe -ChecksumFile .\release\SHA256SUMS
.\install.bat -Version 1.0.0
.\uninstall.ps1
```

```bash
bash install.sh --binary ./release/le-linux-amd64 --checksum-file ./release/SHA256SUMS
bash install.sh --version 1.0.0
bash uninstall.sh
sudo bash install.sh --system --binary ./release/le-linux-amd64 --checksum-file ./release/SHA256SUMS
sudo bash uninstall.sh --system
```

## WinGet portable package

The generator uses the current community schema 1.28.0 and produces three
manifest files under the exact `winget-pkgs` repository partition:

```text
manifests/n/nullvaluefound/Le/1.0.0/
  nullvaluefound.Le.yaml
  nullvaluefound.Le.installer.yaml
  nullvaluefound.Le.locale.en-US.yaml
```

`InstallerType: portable` and `Commands: [le]` expose `le`. No MSI or custom
WinGet uninstaller is introduced; WinGet owns its own package location and
command link. Manual WindowsApps installation and WinGet installation are
separate channels. Do not mix them and assume they update the same executable.

Official schemas are vendored from the pinned Microsoft revision recorded in
`packaging/winget/schemas/SOURCE.json`, with its upstream license. Generate and
validate after downloading the immutable public Windows artifacts and hashes:

```powershell
gh release download v1.0.0 --repo nullvaluefound/le --pattern 'le-windows-*.exe' --pattern SHA256SUMS --dir release
python packaging/release.py winget --version 1.0.0 --artifacts release --output build/winget-submission
python packaging/validate_manifests.py build/winget-submission --winget-client
```

Before initial submission, use an isolated Windows Sandbox/runner to enable
local manifests, install from the generated manifest, execute `le --version`
from a fresh shell, and uninstall the test package. Do not run destructive
package-manager tests against a developer's real installation.

For initial community submission, fork `microsoft/winget-pkgs`, copy the generated
`manifests/n/nullvaluefound/Le/VERSION` directory into the fork, validate it,
sign the Microsoft contributor agreement if requested, and open a version-specific
pull request. The `winget-manifest.yml` workflow stages this directory as an
artifact; it does not submit, merge, or approve public PRs. Later versions use
new version directories and new hashes. The package is not searchable through
`winget install --id nullvaluefound.Le -e` until approval and indexing complete.

## Debian packages and command collision

`le-cli` is the package name; `/usr/bin/le` is the executable. The unrelated
Debian package `le` is a text editor and cannot coexist at the same file path.
The pre-install check refuses either that installed package or any existing
`/usr/bin/le` not owned by `le-cli`. It does not declare Replaces/Conflicts that
would cause APT to automatically remove the editor, and never uses force-overwrite.
Users must resolve the collision explicitly or choose a separate per-user install.

Packages contain control metadata, an ownership-safe preinst, the executable,
real project licensing, documentation/manpage/changelog, and checksums. Archive
ownership is root:root; the executable is 0755. XZ compression supports the older
repository tooling on supported Debian/Ubuntu baselines. No `/usr/local` files
or shell-profile modifications are included in an APT package.

```bash
python packaging/release.py deb --binary release/le-linux-amd64 --version 1.0.0 --output release
dpkg-deb --info release/le-cli_1.0.0_amd64.deb
dpkg-deb --contents release/le-cli_1.0.0_amd64.deb
lintian --fail-on error release/le-cli_1.0.0_amd64.deb
sudo apt install ./release/le-cli_1.0.0_amd64.deb
sudo apt remove le-cli
sudo apt purge le-cli
```

## Signed APT repository

Production URL: `https://nullvaluefound.github.io/le` (active).
`reprepro` maintains `pool/main/l/le-cli` and `dists/stable/main/binary-ARCH`.
Only supplied/tested architectures are indexed. Prior payloads are retained in
pool, while the latest version is indexed for upgrades. Every snapshot is signed
with OpenPGP (`InRelease` and `Release.gpg`) and verified with a dedicated keyring.
Release metadata expires after 30 days; the weekly publication workflow refreshes it.

The publisher also signs an exact file/hash manifest for its private repository
state snapshot before attaching it to the GitHub Release. A later run trusts a
snapshot only after checking its key fingerprint, detached manifest signature,
all file hashes, and repository signature. Untrusted archives cannot supply
symlinks, device files, traversal paths, unverified reprepro config, or database
state to a credentialed signing job. Concurrent publications are serialized.

The Pages payload contains only pool, indexes, public keys, and fingerprint data.
The dedicated temporary GNUPGHOME is outside all release artifacts, is deleted
after signing, and its agent is stopped. No private key belongs in this repository.

### One-time signing setup

1. Create or select a dedicated OpenPGP signing key under the project's control.
   Use a protected offline backup and a passphrase; retain its revocation certificate.
2. Independently verify the full primary fingerprint and put it in
   `apt_signing_fingerprint` in `packaging/distribution.json`.
3. In GitHub environment `apt-release`, set `APT_SIGNING_KEY` to the armored
   secret-key export and `APT_SIGNING_PASSPHRASE` to its passphrase. Never put
   either value in a command line, commit, build log, or release artifact.
4. Restrict the environment to trusted default-branch workflows and protect that
   branch. Do not grant signing secrets to fork PRs or unreviewed tag code.
5. Set repository Pages source to GitHub Actions. The Pages deployment uses a
   separate `github-pages` job with only Pages and OIDC permissions.

`publish-apt.yml` is dispatched on the default branch after the complete GitHub
Release is public; a weekly default-branch run refreshes the latest snapshot.
Signing code is checked out from that trusted branch. Downloaded packages are
verified as data and never executed by the job holding production secrets.
Missing metadata/secrets, bad fingerprints, bad checksums, invalid signatures,
and downgrades fail before deployment.

### Client trust bootstrap

Verify the signing fingerprint through an independent trusted channel first.
The project's Ed25519 archive key is
`9ECD6CC083C1EE9EF8EDD26240167FE47E9E1C26`, expiring on 2029-11-06 UTC.
Its public key is tracked under `packaging/apt/`; private recovery material is
kept outside the repository. The local recovery bundle uses Windows DPAPI and
requires the original Windows account and computer; it is not by itself a
portable off-site backup.

```bash
sudo bash packaging/setup-apt.sh --fingerprint 9ECD6CC083C1EE9EF8EDD26240167FE47E9E1C26
sudo apt update
sudo apt install le-cli
```

The script fetches the selected public key over HTTPS, verifies the fingerprint,
and creates `/etc/apt/keyrings/le-archive-keyring.gpg` plus a Deb822
`/etc/apt/sources.list.d/le.sources` with `Signed-By`. It does not weaken APT
signature checking or install a globally trusted key.

```bash
sudo apt update
sudo apt upgrade
sudo apt remove le-cli
sudo apt purge le-cli
# Repository removal is separate and does not remove the application:
sudo bash packaging/setup-apt.sh --remove-repository
```

The repository bootstrap tracks its own files and preserves user modifications.
Ordinary package removal never deletes repository configuration.

### Key rotation

Generate a new dedicated key, preserve the old public key and recovery backup,
and publish the new key's full fingerprint through the same trusted channel.
Before switching repository signatures, have clients rerun the bootstrap with
the new verified fingerprint during a planned transition. Retain prior public
keys under `keys/FINGERPRINT.gpg`; they are public records, not secrets.
Record the former fingerprint in `apt_trusted_previous_fingerprints` so a new
signing workflow can verify the previous signed state snapshot. Update the
configured active fingerprint and protected secrets together, dispatch a signed
refresh, and verify both signatures and a clean client's apt update. Clients
that have not refreshed their pinned key will correctly reject the new key;
never work around that by disabling authentication.

## Release workflow and exact commands

```bash
python -m pip install -r requirements.txt -r packaging/requirements-build.txt
python packaging/generate_manual.py
python packaging/release.py build --version 1.0.0 --output release
python packaging/build_test_fixtures.py
python -m unittest discover -s tests -v
python packaging/release.py checksums release
# Linux with reprepro, gnupg, dpkg-dev, gcc, lintian and Docker available:
python packaging/test_apt.py --binary release/le-linux-amd64 --version 1.0.0 --containers
python packaging/release.py validate-public --version 1.0.0
# After configuring APT signing metadata:
python packaging/release.py validate-public --version 1.0.0 --require-apt
git tag v1.0.0
git push origin v1.0.0
```

The release workflow builds and tests native binaries with read-only permissions.
A protected `release` publishing job uses trusted default-branch code, verifies
tag ancestry/source hashes/version/header/hash, creates real Debian packages,
assembles manual installers, and uploads a draft release completely before
making it public. Only then does it dispatch WinGet staging and, when
`LE_APT_ENABLED=true`, APT publishing. The first APT publication is a manual
dispatch after signing setup; enable automatic updates after that succeeds.
Actions are pinned to exact official commits. Production signing credentials
are not passed to build jobs, pull requests, or tagged application code.

Initial required repository settings:

- Public `nullvaluefound/le` repository with Actions enabled.
- Trusted default branch and release tag protections; reviewed workflow updates.
- Protected `release` and `apt-release` environments. Restrict apt-release to
  default-branch dispatches and schedules; do not allow unreviewed tags access.
- `APT_SIGNING_KEY` and `APT_SIGNING_PASSPHRASE` in apt-release.
- Real `apt_signing_fingerprint` in project configuration.
- Set `LE_APT_ENABLED=true` only after the first signed publication succeeds;
  this enables the weekly expiry refresh. Manual dispatch still fails safely
  on missing credentials while the repository is being prepared.
- GitHub Pages source: GitHub Actions; `github-pages` environment configured.
- Leave `LE_ENABLE_ARM64` unset until both native ARM64 builds and tests pass,
  then add arm64 to configuration and set the repository variable to true.

No automatic WinGet submission token or public-PR approval is configured.
For an unusual Python distribution with no discoverable runtime license file,
set the build-only `PYTHON_LICENSE_FILE` to its actual license text. Each binary
contains its MIT/runtime/dependency notices and has a matching `.LICENSES.txt`
release artifact; Debian packages also retain those notices under `/usr/share/doc`.

## Troubleshooting

**No release found:** builds/workflows are not themselves public releases. Finish
release metadata configuration and publish a version tag successfully first.

**Wrong architecture or glibc:** use the artifact whose header/build metadata
matches your OS/architecture and glibc baseline. Do not rename an incompatible
binary and assume compatibility. Build on an older supported baseline if needed.

**Command still resolves to an old copy:** open a fresh terminal, inspect
`Get-Command le -All` or `type -a le`, and remove/update through the manager that
owns each copy. A manual installer does not commandeer another manager's files.

**Changed binary, record, or PATH block:** the installer preserves it. Inspect
your changes and reconcile ownership intentionally before retrying; the scripts
do not remove unrelated content to force success.

**APT signing or expiry failure:** fix the protected key/agent configuration and
publish a verified snapshot. Never suppress verification. If publication has
paused beyond 30 days, dispatch a signed metadata refresh.

**WinGet not searchable:** community approval and indexing are external steps.
Use a verified manual artifact until the package is actually listed.
